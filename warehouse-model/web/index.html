Why does this matter? — reading the model

Storage capacity is pure geometry: how many rack rows fit across the building's width, how many bays fit along its length, times levels and positions per bay. Change aisle_width and watch fewer or more rack rows fit — a physical consequence, not a tuning knob on the capacity number itself.

Utilization is deliberately independent of capacity: current_inventory_pallets is a real-world operating fact (how much is actually in the building right now), so shrinking capacity without changing demand is exactly how utilization climbs past 100% — a genuine overflow condition, not a clipped display.

Travel distance comes from a simplified rectilinear (Manhattan) distance model — half the racking block's width, plus half a row's length, plus the cross-aisle clearance, doubled for a round trip. It's the standard textbook approximation for a rectangular storage block: good for showing how layout choices trade off against travel, not precise enough to schedule a fleet against.

Cost uses flat illustrative rates (see the Cost sliders) — it shows how racking, building shell and dock costs shift relative to each other as the design changes, not a quotation.

Guided experiments — try these
  1. Geometry. Double warehouse_length. Does storage capacity double too? (Watch bays_per_row in the Traceability panel — the two cross-aisles are a fixed cost, so a longer building is slightly more efficient per metre, not exactly double.)
  2. Capacity without footprint. Leaving warehouse_length and warehouse_width untouched, can you raise storage capacity by changing only rack_height and levels_per_rack? What has to be true of clear_height for that to work?
  3. Utilization under fixed capacity. Freeze the building and racking parameters. Raise current_inventory_pallets past the storage capacity shown in Key Results. What warning appears, and what does that mean operationally?
  4. A trade-off. Narrow aisle_width to fit more rack rows. Capacity rises — but does Avg. Round Trip rise, fall, or stay flat? Why might a real facility still avoid the narrowest legal aisle?
  5. The bottleneck shifts. Push daily_throughput_pallets up while holding dock count fixed. At what point does Dock Utilization — not storage — become the binding constraint?
How this is built — architecture

freecad/create_model.py is the authoritative engineering model: it reads data/parameters.json, builds the warehouse in FreeCAD (floor/walls/roof via Part::Box, a live Spreadsheet::Sheet holding every parameter as a named, unit-tagged, expression-bindable cell), and exports a tessellated GLB snapshot. Toggle Reference Model above to load that real export.

web/src/calculations.js is the analytical model — the same layout arithmetic FreeCAD's script runs, reimplemented in JS so it can recompute instantly as you drag a slider, with every function returning a trace array (see the Traceability panel).

web/src/visualization.js is the live 3D view: procedural Three.js geometry built from the same parameters and the same layout numbers, rebuilt on every change. It is not the GLB — a baked mesh can't resize itself — and the app never implies otherwise.

This is Phase 1 of the project: parametric model, analytical model, live 3D, KPIs, charts, explanations and traceability, all connected and tested end to end. Guided lessons, saved scenarios with side-by-side comparison, a sensitivity-analysis mode, a before/after view and CSV/JSON export are the planned Phase 2 layer on top of this same architecture — see the project README.

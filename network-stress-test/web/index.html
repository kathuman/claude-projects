How the solver works

Each product is solved as its own min-cost flow problem (successive shortest augmenting paths with node potentials), production and warehouse nodes are node-capacitated via the standard split-node technique, and consumer demand is the sink. Products are solved sequentially in ascending priority order, each consuming from whatever edge capacity earlier products left behind. This is a deliberate, documented approximation of the much harder general multi-commodity flow problem — a higher-priority product claims a shared lane first; a lower-priority one gets only the leftover. It is not a global joint optimum across products.

A scenario disables or derates specific nodes/lanes to model a disruption before re-solving — compare Key Results before and after. The N-1 scan automates this: it tries disabling every currently-active node and lane, one at a time, and ranks them by how much service level each single loss costs — the power-grid "N-1 contingency" idea applied to a supply network.

About the generated starting network

"Generate" produces a random network clustered around real-world trade regions so the map looks plausible, with mode-characteristic lane defaults and a coverage pass that guarantees every node has at least one upstream path for each product it handles — but it is not calibrated to a pristine 100% baseline service level. A freshly generated network typically clears only 55-70% of demand out of the box, the same way a real, un-optimized network would: some lanes are genuinely capacity-constrained, some nodes are one hop further from supply than others. That's an intentional, honest starting point for a stress-testing tool, not a bug to chase to zero — edit capacities, add lanes, or regenerate with a different seed/fanout to explore how those choices change resilience.

Phase 2 — Monte Carlo, Time-to-Survive/Recover, and adversarial search

Monte Carlo samples many independent random scenarios (each edge fails with its own lane baseFailureRate; each node fails at a configurable rate) and reports the distribution of outcomes — mean, percentiles, worst trial observed — rather than one hand-picked "what if". It assumes independent failures: a real regional event that knocks out several correlated lanes at once isn't modeled here.

Time-to-Survive vs. Time-to-Recover compares, for the currently applied scenario, how long a consumer's inventory buffer covers its shortfall (buffer days × pre-disruption receipt ÷ shortfall rate) against how long the disrupted element takes to come back (meanDisruptionDays, per element, defaulting to 14 days for a node and reusing lane defaults for an edge). If time-to-survive is shorter, that consumer stocks out before recovery — the gap is genuine downtime. This is a static, single comparison built on the same solver as everything else here, not a day-by-day dynamic simulation with depleting/replenishing inventories and cascading recovery — an intentional, documented simplification of the full MIT CTL / Sheffi resilience framework this app is built around, not a claim of full dynamic realism.

Adversarial search greedily re-runs the N-1 contingency scan against the network as it's already been degraded by prior steps, each time removing whatever does the most additional damage, up to a budget of simultaneous failures. Like the N-1 scan, this is a tractable heuristic (network-interdiction framing), not a guaranteed globally-worst combination — exhaustively checking every possible combination of even a handful of failures out of hundreds of elements is computationally infeasible.

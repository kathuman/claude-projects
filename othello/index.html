How to play

Players take turns placing a disc of their colour. A move is legal only if it traps one or more of the opponent's discs in a straight line (horizontal, vertical or diagonal) between the disc you just placed and another disc of your colour — every trapped disc then flips. Black moves first. If you have no legal move your turn is skipped; if neither player can move the game ends. Whoever has more discs when the board fills (or both sides are stuck) wins.

Corners can never be flipped, so they are prized; the squares diagonally next to a corner hand it over and are usually poison. The computer knows this.

The board can be 6×6, 8×8 (standard) or 10×10 — the computer builds a fresh positional map and adjusts its search depth for each. Disc and board styles under Look are cosmetic and are remembered between visits.

How the code is built

The whole game is this one HTML file — no build step, no libraries. All the JavaScript lives in a single function (an IIFE) at the bottom, split into labelled sections with // === banners. Those sections form three layers that deliberately never reach across each other:

  • The rules (BOARD LOGIC) — pure functions over a 2-D array of numbers. No DOM, no shared state. flipsFor, legalMoves, applyMove, counts. This layer would run unchanged in Node.
  • The brain (AI) — also pure. evaluate scores a board, negamax searches moves ahead, chooseAImove picks one. "Difficulty" is just how deep the search goes.
  • The screen & the glue (RENDER, FLOW, CONTROLS) — the only code allowed to touch the DOM. render() paints state onto the board; FLOW changes state in response to clicks and timers.

The board is just numbers

1 = black, -1 = white, 0 = empty. Storing the two colours as +1 / -1 is the central trick: the opponent of color is always -color. flipsFor walks all eight compass directions (DIRS) from a candidate square, collects a run of -color discs, and keeps that run only if it ends on one of your own discs. That single function is the entire rulebook of Othello.

One source of truth

Everything that changes lives on one object, state — the board, whose turn it is, the move list, the undo history, the chosen size / difficulty / looks. After any change, exactly one function — render() — rebuilds what you see from state. It is idempotent: calling it twice gives the same screen. So the flow code never has to remember to poke a particular label; it edits state and calls render().

A move is a tiny state machine

doMove → save a history snapshot → applyMove (place and flip) → swap turn → resolveTurnState: if the side to move has no legal reply, log a pass and swap back; if neither side can move, the game is over. maybeAIMove then fires if it's the computer's turn — on a short timer, so the flip animation paints first.

Undo is snapshots, not reverse moves

pushHistory clones the whole board onto a stack before each move; undo pops it back. Cloning a small integer array is cheap and avoids ever having to "un-flip" discs.

The AI in three steps

(1) evaluate(board, color) returns a single number: weighted square values (WEIGHTS) + mobility (how many moves each side has) + a large bonus for owned corners, blended differently in the opening, midgame and endgame. (2) negamax is minimax in its compact form — the opponent's best reply is just -negamax(…) — with alpha-beta pruning to skip branches that cannot change the result, and move ordering (try high-value squares first) to make the pruning bite. (3) chooseAImove sets the depth from the difficulty button (Easy is mostly random; Expert looks ~6 plies ahead) and switches to a full solve once few squares remain.

Any board size from one generator

buildWeights(n) builds the positional map for a 6, 8 or 10 board from the shape of each square — its distance to the nearest edge and corner — instead of a hard-coded 8×8 grid. Corners score 120, the squares hugging them −20 / −40, edges +20 / +5, the centre +3.

Look = CSS variables + a data attribute

Disc and board colours are CSS custom properties. Choosing "Walnut" just sets data-board="walnut" on <html>; a CSS rule redefines the variables; the browser repaints. The only JavaScript involved is saving the choice to localStorage.

How the HP 48 works, from the chip up

When you press 2, ENTER, 3, + on a 48GX, the processor runs about 90,000 instructions before the 5 appears (I counted them in this emulator). This page follows them: what the processor is, how it talks to memory, how the keyboard and screen are wired, and how the calculator's built-in software (the ROM) turns key presses into maths. Everything here is what this emulator actually does. You can step through a small program on the emulator's own processor code.

01What's inside

Open a 48GX (it came out in 1993) and you find one main chip that does almost everything, a ROM chip, a RAM chip, a crystal, the display and the keyboard. The main chip contains the Saturn CPU, the processor HP designed for its calculators in the 1980s, plus the controllers for the display, the timers and the keyboard.

The CPU does not "know" it is in a calculator. It only reads instructions, does arithmetic in its registers, and reads and writes memory. Everything that makes it a calculator — the stack, the menus, the maths functions, even drawing the digits on the screen — is software stored in the ROM.

02Counting in nibbles

Most computers you know work in bytes (8 bits). The Saturn works in nibbles: 4 bits, one hexadecimal digit, 0 to F. That suits a calculator, because one decimal digit (0–9) fits in one nibble.

  • Addresses are 20 bits, five nibbles, from 00000 to FFFFF. That is 1,048,576 places, and each place holds one nibble. So the whole address space is 1 M nibbles = 512 KB, exactly the size of the 48GX's ROM.
  • Numbers are stored low nibble first. The address 80123 is written into memory as 3 2 1 0 8. This trips everyone up at first, including me: my first test programs wrote addresses the wrong way round.

Hex in one line. Hexadecimal counts 0 1 2 … 9 A B C D E F, then 10. So hex C is 12, and hex 10 is 16. One hex digit = one nibble = 4 bits.

03The CPU's registers

Registers are the CPU's own tiny, very fast memory. The Saturn has unusually wide ones: A, B, C and D are each 16 nibbles (64 bits), wide enough for a whole floating-point number. Arithmetic only happens in these.

RegisterSizeWhat it is for
A B C D16 nibblesworking registers: all arithmetic and logic happens here
R0 … R416 nibblesscratch storage: copy A or C in and out, but no arithmetic
D0 D15 nibblesdata pointers: the addresses the CPU reads and writes memory through
PC5 nibblesprogram counter: the address of the next instruction
P1 nibblea pointer to one nibble inside a register (see fields below)
RSTK8 × 5 nibblesreturn stack: where a subroutine call remembers where to come back to (only 8 deep)
ST, carry, modebitsstatus flags; the carry from the last addition or test; hex or decimal arithmetic

Fields: working on part of a register

Instructions rarely use all 16 nibbles. Each one names a field, a slice of the register. The same "add C to A" instruction can add just the address part, just the exponent, or the whole thing.

04Fetch, decode, execute

A CPU does one thing over and over:

  1. Fetch: read the nibble at the address in PC, and move PC on by one.
  2. Decode: work out which instruction it is. On the Saturn, instructions are 2 to 21 nibbles long, so the first nibbles decide how many more to read. D A means "copy C into A, address field"; 3 means "load a constant into C", and the next nibble says how many digits follow.
  3. Execute: do it: change a register, read or write memory, or (for a jump) change PC.

Then repeat: on the 48GX, roughly half a million times a second while it is busy. That is all a CPU ever does. Some example instructions, with their real encodings:

The calculator does all its maths in BCD, which is why 0.1 + 0.2 is exactly 0.3 on a 48, unlike in most programming languages.

    05Memory and the bus

    The CPU has one way to reach the outside world: put an address on the bus and read or write a nibble. What answers depends on the memory controller, which decides which chip lives at which address.

    On the 48GX that map is not fixed: the software builds it when the calculator starts. At power-on only the ROM is visible. The ROM's first job is a little conversation using three special instructions:

    • C=ID asks "who is the next unconfigured device, and how big is it?"
    • CONFIG answers "then you live at this address".
    • UNCNFG takes a device away again (used to check the plug-in card slots).

    The devices sit in a chain, and each CONFIG places the next one. On a real boot, which you can watch in the emulator, the ROM puts the 64 I/O registers at 00100 and the 128 KB of RAM at 80000, then probes the two card ports.

    The I/O registers are how software controls hardware. They look like memory, but writing to them does something: turn the display on, set its contrast, say where in RAM the picture is, start a timer. Reading one tells you something: which keys are down, what a timer says. This trick is called memory-mapped I/O, and almost every computer uses it.

    06The keyboard

    49 keys, but nowhere near 49 wires. The keys sit on a grid of 9 output lines and 6 input lines, with a key at each crossing. To find out which key is down, the CPU:

    1. switches on one output line (instruction OUT=C),
    2. reads the input lines (C=IN): a bit is 1 if a key on that output line is pressed,
    3. does that for each line in turn. This is called scanning.

    I found the first two key positions on the real ROM by brute force: press every line/bit pair while the ROM asked "Try To Recover Memory?" and watch which one answered NO. The rest come from the documented matrix, and every one is checked by typing sums on the real ROM.

    07The screen

    The display is 131 × 64 pixels, one bit each, and its picture lives in ordinary RAM. The I/O registers tell the display controller where it starts. Each row takes 34 nibbles (136 bits, a few more than the 131 visible), and within a nibble the leftmost pixel is the lowest bit. To draw the digit "5", the ROM simply writes the right bits into RAM; the display controller keeps reading that RAM and showing it, about 64 times a second.

    The bottom 8 rows can come from a second address. That is how the menu labels (the boxes above the top row of keys) can stay put while the rest of the screen scrolls.

    08Sleep, timers and interrupts

    A 48 can run for months on three AAA batteries because the CPU is asleep almost all the time. When the ROM has nothing to do, it runs SHUTDN and the CPU stops completely. Two things can wake it:

    • A key press. The keyboard raises an interrupt: the CPU saves where it was on the return stack and jumps to address 0000F, where the ROM's interrupt handler starts.
    • A timer. Timer 1 is 4 bits and counts down 16 times a second. Timer 2 is 32 bits and counts 8192 times a second; it is the calculator's clock. When a timer passes zero it can wake the CPU or interrupt it.

    Time keeps passing while the calculator is off, because timer 2 keeps counting. This emulator does the same thing when you close the page: next time, it moves timer 2 on by the time you were away, so the clock is still right.

    09What the ROM is

    The ROM is 512 KB of HP's software, fixed when the chip was made. It holds everything that makes the calculator a calculator:

    • the start-up code that builds the memory map,
    • the keyboard scanner and the interrupt handlers,
    • the font and the code that draws text on the screen,
    • the command line parser that turns what you type into objects,
    • the commands themselves, from + to matrix inversion, symbolic algebra, plotting and the equation solver.

    The emulator doesn't contain any of it. It only builds the hardware (CPU, bus, timers, keyboard, display) and then runs your copy of the ROM. If the hardware is right, the software works on its own, which is how this whole project was tested.

    10RPL: a language running on a language

    Most of the ROM is not written in Saturn machine code. It is written in RPL, HP's own language, and machine code is only used for the innermost, fastest parts. This is the most interesting idea in the calculator.

    Everything is an object

    Every value the calculator handles is an object in memory: a real number, a string, a list, a program. Every object starts with the 5-nibble address of its prolog, a small piece of machine code that knows what kind of object it is. A real number starts with the address 02933, a string with 02A2C, a list with 02A74, a program with 02D9D.

    A program is a list of addresses

    An RPL program is not machine code. It is a list of addresses of other objects and commands, one after another, 5 nibbles each. To run it, the CPU uses register D0 as the RPL instruction pointer and does this, forever:

    So when an RPL program says "+", the loop reads the address of the + command, jumps to it, the command adds the top two numbers on the stack, and its last instructions are the loop again, which fetches the next address. A whole high-level language running on three machine instructions: this design is called threaded code.

    The stack

    The stack you see on the screen (levels 1:, 2:, 3: …) is a list of pointers in RAM, each pointing at an object. Register D1 points at it while RPL runs. When the calculator is idle, it keeps the address of level 1 at 806F8. This emulator found that address by putting 7, 8 and 9 on the stack and searching RAM for a pointer that led to them, and that is how the stack panel on the calculator page reads your results.

    11How a number is stored

    A real number is 21 nibbles: the prolog address 02933 (written low nibble first), a 3-digit exponent, a 12-digit mantissa and a sign, all in BCD. Try one:

    grey prolog · blue exponent · amber mantissa · green sign. Shown in memory order, lowest address first.

    A negative exponent is stored as its 10's complement: 10−3 is stored as 997. The sign is 0 for positive and 9 for negative. With 12 digits of mantissa, every result is exact to 12 significant digits, which is why the supply chain toolkit can check the calculator's answers "to 12 digits".

    12One key press, start to finish

    Put it all together. You have typed 2, ENTER, 3 and now press +:

    1. The CPU is asleep in SHUTDN. Pressing + connects output line 0 to input bit 0, and the keyboard raises an interrupt.
    2. The CPU wakes, pushes its place onto the return stack and jumps to 0000F.
    3. The ROM's handler scans the 9 lines, finds line 0 / bit 0, turns it into a key code and puts it in a key buffer in RAM. It keeps scanning until the key is released, so one press counts once.
    4. The main loop takes the key from the buffer. There is a command line with 3 on it, so it first parses that: the text "3" becomes a real-number object, and a pointer to it goes on the stack.
    5. The + key runs the + command: an RPL object, run through the inner loop. It checks levels 1 and 2 are numbers, then machine code adds the two numbers in BCD (decimal) arithmetic, lining up their exponents first.
    6. The result, a new real-number object 5, is written to RAM and its pointer replaces the two on the stack.
    7. The display code draws "1: 5" by writing font bits into the screen area of RAM. The display controller shows it.
    8. Nothing left to do: the ROM runs SHUTDN, and the CPU sleeps until the next key.

    By the emulator's count that is about 90,000 instructions and around a tenth of a second of the 48GX's time. Steps 3 to 7 are simplified: the ROM's own routines for each are long, but this is their shape. In the emulator, it is the same instructions, run in JavaScript.

    13How the emulator fakes all of this

    An emulator is a program that behaves, nibble for nibble, like the hardware. This one has four parts:

    • The CPU (src/saturn.js): a function that does fetch, decode and execute for one instruction, written from the Saturn documentation.
    • The machine (src/machine.js): the bus, the memory controller's chain, the 64 I/O registers, the two timers and the key lines. When the CPU reads an address, the machine decides whether ROM, RAM or an I/O register answers.
    • Timing: each instruction is counted in clock cycles. Sixty times a second the page runs about 61,000 cycles (3.6864 MHz ÷ 60), advancing the timers as it goes. When the CPU sleeps, the emulator skips straight to the next timer tick, so an idle calculator costs almost nothing.
    • The page: it draws the RAM picture onto a canvas and turns your clicks into key presses on the matrix.

    What the real ROM taught me

    The CPU passed over a hundred checks I wrote myself, and was still wrong in two places, because my tests shared my mistakes. The real ROM found both:

    • The logic instructions. I had half the AND and OR instructions wrong. The ROM stopped on one of them during start-up.
    • The checksum hardware. The 48 has a circuit that computes a running checksum (a CRC) of the memory it reads, and the ROM uses it to check its saved clock. I let instruction fetches feed the checksum too. The real chip only counts data reads, so the ROM's check never matched, it decided the clock was corrupt, and it restarted itself forever, a few times a second.

    That is the general lesson of emulators, and of testing: the best test is the real thing. HP's ROM was written for the real chip, so if it runs, the chip is right.
